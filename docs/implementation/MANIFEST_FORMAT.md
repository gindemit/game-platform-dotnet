# Execution manifest schema v1

`execution-manifest.json` is the single task/dependency/feature-completion ledger for this paired plan. Detailed ordered steps live at each `card` path/anchor. The JSON is not a second architecture specification. Validate with `python docs/implementation/validate_manifest.py`; unit tests exercise hostile planning edits. The checker proves structural consistency only, not implementation truth.

Root fields: `schema_version` = 1; `planning_only` = true (the artifact is a planning ledger even after task evidence is added); `baseline_commits` maps exact owner/repository names to inspected SHA; `canonical_cards` locates the three task books; `external_prerequisites` maps stable named gates to required evidence; `tasks` is a nonempty array; `feature_ledger` contains exactly the existing sixteen modules. Optional `peer_evidence` maps a satisfied external gate to a reviewed evidence record, never a bare claim inferred from task status.

Every task has: `id` (CL-xxx or INT-xxx), `title`, `owner_repo`, `role`, `milestone` (SDK milestone / Unity A–E phase), `dependencies` (task IDs only), `status`, `blocked_reason`, `owned_paths`, `locks`, `acceptance_ids`, `test_environment`, `peer_dependencies` (external keys only), `baseline_commit`, `card`, `evidence_paths`, `evidence`, and nonnegative integer `wave`. Optional `conditional_acceptance_ids` records future conditional gates such as DI10/11; it never means passed.

Task status values are planned, in_progress, blocked, complete. Blocked requires a reason; complete requires evidence. Source reality is recorded separately in AUDIT/module ledgers: implemented, stubbed, planned, unverified and blocked must not be conflated. Owned paths are repository-relative exact paths or directory prefixes, not arbitrary globs. New paths are proposals until created by the task; existing path/type claims are identified in its card/audit. Evidence/status documentation updates are coordinator-owned even when workers provide patches.

Two same-wave tasks in the same repo cannot share a lock or equal/ancestor owned path. Cross-repository interface dependencies still require handoff review; absence of a filesystem collision is not semantic independence. A dependency must exist, cannot create a cycle, and must have an earlier conservative wave. Waves are not global wait barriers: ready independent work can continue around blocked peer gates, with locks and validation preserved.

Acceptance IDs A01–A13 come from MrSquare `Docs/Architecture/PlatformRepositories/ACCEPTANCE.md`, not the older A05–A11 findings register. LC01–13 and DI01–12 come from the adopted lifecycle/DI documents. Environment labels identify separate evidence: python, dotnet, sqlite (real native desktop), unity, device and peer (real cross-language/server). They are requirements, not available-runner assertions.

Each feature row contains `feature`, `sdk_task`, `integration_tasks`, `sdk_status`, `mrsquare_integration_status`, `sdk_evidence`, `mrsquare_evidence`, `package_compatibility`, `backend_compatibility`. SDK statuses: stubbed, planned, implemented, unverified, blocked. Unity statuses: not_installed, planned, wired, integrated, unverified, blocked. Implemented requires a complete SDK task and evidence; integrated additionally requires complete mapped integration tasks, independent consumer evidence and non-null exact artifact/backend compatibility. Review must also enforce live/device gates from the card; a syntactically populated evidence list is not proof.

Evidence records should carry commit/artifact/schema/fixture versions, command/tool/device environment, exit code and nonzero executed-test count, raw artifact paths, expected/actual result, fake-versus-real provider, reviewer and blocked/unrun cases. Never commit secrets or production player data. Compatibility must name exact tested commits/digests, not moving branches or `latest`.
