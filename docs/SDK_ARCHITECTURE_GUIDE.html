Three repositories, three authorities

This is the cleanest way to avoid overlap with the separate backend review.

Backend repository

Protocol and server authority

Owns canonical schemas, endpoint semantics, authorization, PostgreSQL mutations, business-source uniqueness, reward/value authority and hosted deployment.

Referenced here only as: reviewed contract snapshots, semantic ports and external acceptance gates.

This repository

Portable client SDK

Owns C# domain/port contracts, feature policy, local durability, sync policy, MessagePack/HTTP/SQLite adapters, tests and deterministic Git UPM production.

Does not own: backend SQL/functions or Unity game UI/rules.

Unity consumer repository

Host and game integration

Owns composition root, Unity executors, secure secrets, filesystem paths, game checkpoint writes, projection mapping, UI/presentation and device acceptance.

Consumes: one exact reviewed Git UPM commit.

Rule of thumb: the backend decides what is authoritative; this SDK decides how a portable client safely stores, sends and observes it; the Unity game decides how it is composed and presented.

Types stay separated

Domain/read models live in feature contracts. Wire DTOs live in Wire.Contracts. Remote semantics live in Backend.Contracts. Storage values/transactions live in Storage.Abstractions. SQLite rows remain adapter-internal.

Lifetime stays explicit

Infrastructure may outlive an application. Account scopes may not. Owner scope is backend + app + account; view generation fences late results. Borrowed transactions cannot be retained or committed by feature code.

Failure is honest

Unsupported paths throw or return explicit unavailability. No fake authentication, Ready state, grant, acknowledgement, transaction, local value authority or JSON decode fallback is allowed.

Packaging is delivery, not a fork

src/ is the runtime source of truth. upm/ is generated deterministically with 15 SDK DLLs, the exact MessagePack closure, selected SQLite native libraries, metadata and notices.

The first-account and offline-command journey

This sequence explains the architecture better than a class list. Every transition has a precise authority boundary.

1
AuthenticateHost-supplied lifecycle obtains a principal-specific session. Tokens remain memory-only; secrets use a host secure-store seam.
2
Provision onlineThe SDK reserves installation + stream IDs durably, then validates the backend-issued account mapping.
3
Bootstrap atomicallyPages stage invisibly. Only a complete final snapshot installs projections, cursor and Ready at one boundary.
4
Commit local intentGame checkpoint callback + provisional projection + sequence + immutable command bytes enter one SQLite transaction.
5
Push in orderOnly the next contiguous command is leased. Retries preserve operation, stream, sequence, source and fingerprint.
6
Observe receiptAcceptance becomes “accepted awaiting pull.” A receipt never edits confirmed wallet/inventory/entitlement value.
7
Pull and confirmA committed feed group installs all component projections and cursor atomically; matching evidence can then confirm presentation.
Reset and restored-server behavior

A visibility-generation change or expired retention causes snapshot replacement while preserving the immutable outbox. If a server boundary regresses below local terminal state, the coordinator reconciles every receipt above that boundary. Only genuinely absent receipts at the exact observed watermark return to pending with the same identity; conflicts or persistent stale boundaries block with StreamRecoveryRequired. Push acknowledgements never move pull cursors.

Why “receipt” and “confirmed value” are different

A successful push or retained receipt proves a command outcome, not that a client projection has observed the authoritative value mutation. Wallet, inventory, entitlements and reward presentation wait for the ordered pull/snapshot path. This prevents double-application and fabricated revisions.

Prioritize RewardFulfillment C5/C6/C10 and Progression R09 C7 because they are explicit, localizable correctness gaps in already-used code. Add focused real-SQLite restart/reset tests for each.

2. Finish current frozen-contract mappings

Complete production private-sync mapping/codecs for Profiles, Inventory, Wallet, Entitlements, Progression and reward correlation where the canonical contract already contains enough information. If it does not, stop at the port and request a backend contract delta—do not invent fields locally.

Now · sync/transport

3. Close CL-005/009/010 behavior gaps

Add the remaining approved providers, push backoff/batching and blocked-auth behavior, then expand live disposable peer faults. Preserve exact operation identity and never infer rollback from timeout/cancellation.

Consumer gate

4. Qualify the selected UPM tag

Unity now selects 0.1.0-dev.119 in source. Verify exact package resolution and payload, then run the focused import/Editor and affected IL2CPP/device checks before transferring any older acceptance result to the new pin.

After backend freezes

5. Add breadth by contract family

Recommended sequence: shared Objectives → Quests → Achievements; then Store → Purchases; then RemoteConfig/Inbox; finally Teams/Leaderboards. Each family starts with a reviewed backend schema/semantic package and negative fixtures.

M5 / release

6. Prove reuse and release compatibility

Integrate an independent tiny second game, remove temporary bridges only after reuse proof, run the full cross-app/device matrix, and produce a compatibility release record. Stable publication/distribution remains a separate owner decision.

Do not implement next: a second protocol inside the SDK, backend business logic, local reward/value authority, global service locator, automatic account merge, legacy-save import, JSON fallback, or broad feature shells backed by fakes.

Architecture decisions: settled and still needed

✓

Settled foundations

Game-neutral portable SDK; manual constructor injection; domain/wire/SQL separation; MessagePack; sqlite-net; UUIDv7 for new distributed IDs; signed-64 values; online first-account provisioning; atomic projection/sequence/outbox; receipts separate from confirmed pull; no legacy gameplay migration.

A

Decisions needed before feature breadth

Backend-owned schema/semantics must be frozen for objectives, commerce, social, config and inbox. The key product decisions are occurrence/eligibility identity, purchase verification authority, season/team authorization and inbox attachment claim semantics.

B

Decisions needed in this SDK

Define C6 no-reward completion confirmation, R09 retryable-failure durability, prune/retention policy for confirmed presentation records, and exact adapter behavior when frozen projection rows cannot satisfy feature contracts.

C

Decisions needed at consumer/release boundary

Choose the production Unity composition, supported native platform matrix (macOS remains unexecuted; WebGL SDK integration is excluded today), current-package qualification gate, stable versioning and whether/where a package may be published.

Assessment: no wholesale architecture rewrite is indicated. The present hexagonal/ports-and-adapters shape fits the work. New ADRs are warranted only where an open item changes authority, durable schema, public contracts, platform support or release policy.

Fast code-reading path

Follow one command from neutral identity to wire, local durability, transport and confirmed projection.

  1. Core identity and ownership — learn OwnerScope, typed IDs and numeric rules.
  2. Storage ports — understand caller-owned transactions, outbox admission and sync values.
  3. SQLite adapter — see how those ports become durable and atomic.
  4. Progression service — trace the representative offline completion use case.
  5. Sync policy — follow ordered send, bootstrap, pull and reset.
  6. HTTP composition and MessagePack — see adapter bounds and failure rules.
  7. Reward correlation — see why receipt, projection and presentation are three different facts.
